# Trao - AI Interview Prep Kit Builder

Trao is a robust, full-stack application that transforms raw job descriptions and company URLs into personalized, structured interview preparation kits. It automatically crawls company websites, extracts core requirements using an LLM, generates high-quality technical and behavioral questions, provides spaced-repetition flashcards, and intelligently schedules your study sessions based on the time remaining before your interview.

## 1. Overview & Stack Justification

**Frontend: Next.js (React), TailwindCSS, Lucide React**
Next.js provides a robust routing framework and fast rendering. TailwindCSS enables rapid, highly responsive styling without managing massive stylesheets. Lucide React provides clean, modern iconography.

**Backend: Node.js, Express.js, TypeScript**
Express is lightweight and unopinionated, perfect for building robust REST APIs. TypeScript adds critical type safety, ensuring our complex LLM JSON outputs are rigorously validated across the pipeline.

**Database & Auth: MongoDB (Mongoose), Express-Session**
MongoDB's document-oriented structure is ideal for storing the deeply nested arrays of questions and flashcards generated by the AI. We use traditional HTTP-only session cookies via `express-session` backed by `connect-mongo` for secure, stateful authentication without the complexity of JWT rotation.

**AI Provider: Groq (Model: `openai/gpt-oss-120b`)**
We use Groq for its incredibly low latency, which is essential for a pipeline that makes multiple sequential LLM calls (Extraction -> Meta -> Generation). We specifically target `gpt-oss-120b` (or equivalent open-source heavyweights) for strong reasoning capabilities in JSON mode.

## 2. Setup Instructions

### Local Setup
1. **Clone the repository:**
   ```bash
   git clone <repo-url>
   cd Trao
   ```
2. **Environment Variables:**
   Copy `.env.example` to `.env` in both the `frontend` and `backend` directories.
   Fill in your `GROQ_API_KEY` and `MONGO_URI`.
3. **Install Dependencies:**
   ```bash
   cd backend && npm install
   cd ../frontend && npm install
   ```
4. **Start Servers:**
   ```bash
   # In backend/
   npm run dev
   # In frontend/
   npm run dev
   ```

### Deployment Configuration (Vercel + Render + MongoDB Atlas)
**Frontend (Vercel):**
- Import the `frontend` directory into Vercel.
- Set `NEXT_PUBLIC_API_URL` to your Render backend URL (e.g., `https://trao-backend.onrender.com`).
- A `vercel.json` is provided for optional API rewriting if needed.

**Backend (Render):**
- Create a new Web Service pointing to the `backend` directory.
- Use the included `render.yaml` configuration.
- Set the following environment variables:
  - `NODE_ENV=production`
  - `FRONTEND_URL` (Your Vercel domain, e.g., `https://trao-frontend.vercel.app`)
  - `MONGO_URI` (Your Atlas Connection String)
  - `SESSION_SECRET` (A strong random string)
  - `GROQ_API_KEY`

**Database (MongoDB Atlas):**
- *Important:* Render's Free Tier does not provide static outbound IPs. You MUST set your MongoDB Atlas Network Access allowlist to `0.0.0.0/0` (Allow Access from Anywhere) for the backend to connect. See Known Limitations below.

### Batch CLI Command
To run the automated batch evaluation against unseen cases (Phase 14):
```bash
cd backend
npm run evaluate -- --input cases.json --output kits.json
```

## 3. Architecture & Retrieval Approach

The application uses an asynchronous, state-machine-driven pipeline:
1. **Crawling (Phase 4):** Uses Axios and JSDOM to fetch the `companyUrl`. It explicitly obeys `robots.txt` using `robots-parser`, respects a strict 5MB size limit, validates `Content-Type`, and explicitly avoids private/loopback IPs for SSRF protection.
2. **Keyword Scoring:** Extracted text is chunked and scored against keyword dictionaries (e.g., "culture", "values", "mission"). The top-scoring chunks are retained to keep the context window tight.
3. **Extraction (Phase 9):** The LLM extracts explicit requirements from the Job Description, strictly categorized into `technical`, `behavioural`, and `domain` requirements.
4. **Generation (Phase 6 & 13):** The extracted requirements and company context are fed back into the LLM to generate targeted questions and flashcards.

## 4. Pipeline Sequencing

The `runPipeline` function orchestrates the flow sequentially, updating a `stage` string in MongoDB (`crawling` -> `extracting` -> `generating` -> `scheduling` -> `ready`). The frontend polls the `/api/kits/:id` endpoint and displays a dynamic progress tracker. We utilize bounded concurrency (max 2 parallel calls) to respect LLM rate limits.

## 5. State Representation & Preservation

In the Kit Builder (Phase 12), users can edit flashcards and questions. 
- **State Tags:** Items are tagged with `source: 'generated' | 'edited' | 'manual'`.
- **Practice Mode Tracking:** Flashcards also track `confidence: 'uncovered' | 'low' | 'medium' | 'high'`.
- **Preservation Logic:** When a user clicks "Regenerate", the backend fetches *new* AI content, but runs a strict merge algorithm: any item marked `edited`, `manual`, or with a confidence rating *other* than `uncovered` is permanently protected and carried over to the new kit structure.

## 6. Schedule Allocation Algorithm

The study schedule (Phase 7) is built dynamically based on the user's available `days` until the interview.
- We divide the requirements into `technical`, `behavioural`, and `domain`.
- We assign a `weight` to each category (e.g., technical = 3, behavioural = 2, domain = 1).
- We iterate chronologically day-by-day up to `days - 1`, allocating items proportional to their weight until exhausted.
- The final day (`day === days`) is always reserved as a "Review Day".
- Fallback: If `days === 1`, everything is clamped into a single "Crash Course" review block.

## 7. Known Limitations & Trade-offs

- **MongoDB Atlas Allowlist:** Due to Render's free tier dynamic IPs, Atlas must allow `0.0.0.0/0`. We mitigate this by relying strictly on strong credentials.
- **Render Sleep Behavior:** Render's free tier spins down after 15 minutes of inactivity. If this happens mid-generation, the kit will hang. We implemented a staleness check (Phase 10) that detects kits older than 3 minutes stuck in `generating`, transitions them to `failed`, and surfaces a "Retry" button.
- **Cold Starts:** The first API request after 15 minutes of inactivity will take 30-60 seconds to complete while Render spins the server back up.
- **Crawl Depth & Breadth:** The crawler only fetches the exact URL provided and does not recursively spider the entire domain, meaning deep nested culture pages might be missed if not directly linked or provided.
- **Coverage Caps:** We enforce a hard limit of 2 "coverage passes" (Phase 8) to prevent infinite loops if the LLM refuses to generate a specific obscure requirement.
- **Creativity Requirement:** We explicitly opted out of the optional Creativity Requirement to focus strictly on the stability and security of the core application.
